section: 20. Playback experience and diagnostics
| 10026 | Playback negotiation returns 503 no_transcode_capacity when one account starts the same title on several devices at once | todo | | | 20.260 | | Reproduced live 2026-10-11 with three concurrent GET /api/v1/playback/<file> calls from one account on three device ids: two return 200 and the third returns 503 no_transcode_capacity (repeatable; two concurrent calls both succeed). Root cause: every device that cannot direct-play spawns its own ffmpeg through `reserve_capacity` in `playarr-transcode` (try_acquire on a node-local semaphore, `PLAYARR_TRANSCODE_MAX_CONCURRENT_JOBS`, default 1, set to 2 on the regional servers). `release_replaced_transcodes` in `playarr-api` playback.rs only frees sessions with the same user, device and file, so other devices never share or release a slot; sessions for other start positions or audio tracks cannot be shared either, and an abandoned client holds its slot until the idle reaper (up to about 75 s). Web, webOS and Tizen together need three jobs on a two-slot node, so the third gets 503 and the client treats it as fatal. Proposed fix (needs Opus review, streaming): (1) weight admission, so a video-copy remux, which only encodes audio, takes a quarter of a slot and a full re-encode takes a whole slot (`acquire_many_owned` in `reserve_capacity`); (2) let a second playback session attach to a running transcode with the same file, profile, audio stream and start position (reference count, stop ffmpeg when the last viewer leaves); (3) answer 503 with Retry-After and make the clients wait and retry instead of showing an error; (4) raise the slot count only after (1), as 4K to 720p transcodes already rebuffer on a two-slot 8-CPU node. |
